# Дизайн: удалённый режим сервера (HTTPS + OAuth через Битрикс24)

Дата: 2026-11-13. Статус: черновик на согласование.

## Зачем

Сейчас сервер работает только как расширение `.mcpb` для Claude Desktop: процесс на компьютере пользователя, доступ к порталу по входящему вебхуку от имени одного человека. Нужно, чтобы сервер был доступен «везде» — из claude.ai в браузере, мобильного приложения Claude, Claude Desktop и Claude Code — и чтобы им могли пользоваться другие сотрудники, каждый от своего имени и со своими правами в Битрикс24.

## Цели

- Сервер постоянно работает на Synology NAS владельца, доступен по `https://mcp.example.synology.me`.
- Подключение из клиентов Claude по стандартному MCP-протоколу авторизации (OAuth 2.1 с динамической регистрацией клиента), как ожидают пользовательские коннекторы claude.ai.
- Пользователь входит через страницу входа портала `portal.example.ru`; сервер работает в Битрикс24 от его имени (OAuth-токены локального приложения), а не от вебхука.
- Подключиться может любой активный сотрудник портала.
- Режим «только чтение» на пользователя: (а) человек сам ставит галочку при подключении; (б) администратор задаёт список сотрудников и отделов, для которых режим включён принудительно; (в) глобальный переключатель на весь сервер перекрывает всё.
- Набор инструментов тот же, что в расширении (35 инструментов), с тем же поведением, кроме `disk_file` (см. ниже).

## Не цели

- Несколько порталов на одном сервере. Сервер обслуживает один портал, заданный в настройках.
- Веб-интерфейс администратора. Настройки — переменные окружения контейнера, просмотр подключений — не нужен на первом этапе.
- Разные наборы прав (scopes) для разных пользователей, кроме «только чтение».
- Экстранет-пользователи и внешние гости (коллаберы).
- Замена режима `.mcpb`/вебхука: он остаётся как есть.

## Анти-цели (провал, даже если «работает»)

- Доступ к данным портала для того, кто не является активным сотрудником портала.
- Один пользователь видит или действует от имени другого (перепутанные токены, общий кэш между пользователями).
- Токены (наши или Битрикс24) попадают в логи, в ответы инструментов или в репозиторий.
- Сломан режим `.mcpb` (stdio + вебхук) или его тесты.
- Пользователь в «только чтение» может что-то изменить в портале.

## Ограничения и факты

- Портал `portal.example.ru` (коробка) доступен из интернета; `https://portal.example.ru/oauth/authorize/` отвечает. NAS — в другой сети, ходит на портал через интернет.
- Коробочный портал обменивает код авторизации на токены через `https://oauth.bitrix.info/oauth/token/` (доступен). Это главный внешний риск; проверяется первым шагом (спайк).
- Токен доступа Битрикс24 живёт 1 час, refresh-токен — 28 дней, при обновлении выдаётся новый refresh-токен.
- REST-вызовы с OAuth: `{client_endpoint}{method}.json` с параметром `auth=<access_token>`; `client_endpoint` приходит в ответе на обмен кода (`https://portal.example.ru/rest/`). Истёкший токен даёт ошибку `expired_token`.
- Локальное приложение в REST создать нельзя — администратор создаёт его в интерфейсе портала (раздел «Настройка на портале»).
- NAS: DSM 7.2, Container Manager (Docker) установлен. `example.synology.me` и `mcp.example.synology.me` резолвятся на NAS; порт 443 открыт; HTTPS — через обратный прокси DSM и сертификат Let's Encrypt с поддоменами.
- Node.js: в контейнере Node 24 (встроенный `node:sqlite`). Расширение `.mcpb` по-прежнему требует Node ≥ 18 и не должно зависеть от `node:sqlite` и express.
- MCP SDK 1.32 уже содержит `StreamableHTTPServerTransport`, `mcpAuthRouter` (метаданные, регистрация клиента, authorize, token, revoke) и `requireBearerAuth`. express — транзитивная зависимость SDK; в `package.json` добавить явно.

## Подходы

Рассматривались три способа, как сервер узнаёт пользователя и действует от его имени:

1. **Вход через OAuth Битрикс24 (выбран).** Локальное приложение на портале; наш OAuth-сервер для Claude «внутри» перенаправляет на страницу входа портала и получает токены Битрикс24 конкретного человека. Плюсы: права самого человека, отключённый сотрудник теряет доступ, ничего не надо создавать каждому. Минусы: нужно приложение на портале, обновление токенов, зависимость от `oauth.bitrix.info`.
2. **Каждый вводит свой вебхук.** Проще, но каждому нужно уметь и иметь право создавать вебхук, вебхуки бессрочные, на NAS копятся долгоживущие секреты, отключение сотрудника не обрывает доступ. Запасной вариант, если спайк с подходом 1 не пройдёт.
3. **Общий вебхук администратора.** Отпал: вебхук всегда действует от имени создателя, разграничить пользователей невозможно.

Владелец выбрал подход 1 с откатом на 2 при проблемах на стороне портала.

## Решения владельца

- Подход 1 (OAuth Битрикс24), откат — подход 2.
- Подключаться может любой активный сотрудник портала.
- «Только чтение» — и галочка пользователя, и принудительный список администратора.
- Адрес: `mcp.example.synology.me`, развёртывание в Container Manager на NAS.
- Подключаться может любой MCP-клиент (открытая регистрация); защита — страница подтверждения с названием и хостом клиента и предупреждением для неизвестных.

## Устройство

### Общая схема

```
Claude (claude.ai / Desktop / Code)
   │  OAuth 2.1 + DCR, Bearer-токен
   ▼
DSM reverse proxy  https://mcp.example.synology.me  → контейнер :3000
   ▼
server/http.js (express)
   ├─ /.well-known/*, /register, /authorize, /token, /revoke   ← mcpAuthRouter + наш провайдер
   ├─ /b24/callback, /consent                                   ← вход через портал и галочка
   └─ /mcp  (requireBearerAuth → McpServer пользователя)        ← инструменты
         ▼
   Bitrix (OAuth-режим, токены пользователя, автообновление)
         ▼
   portal.example.ru/rest/…            oauth.bitrix.info (обмен/обновление токенов)
```

### Разделение кода

- `server/tools.js` — регистрация всех инструментов, вынесенная из `server/index.js`: `registerTools(server, ctx)`, где `ctx` даёт `client()` (экземпляр `Bitrix`), `readOnly` (bool) и `mode` (`"stdio"` | `"http"`). Сейчас код читает глобальные `READ_ONLY`, `DOWNLOAD_DIR`, `client()` — их нужно заменить на `ctx`.
- `server/index.js` — точка входа stdio (как сейчас): вебхук из env, `registerTools` с `mode: "stdio"`. Поведение и вывод не меняются.
- `server/http.js` — точка входа HTTP: express, OAuth, `/mcp`.
- `server/oauth.js` — провайдер для `mcpAuthRouter` (хранилище клиентов, authorize, обмен кода и refresh, отзыв, проверка токена).
- `server/store.js` — хранилище на `node:sqlite`.
- `server/bitrix.js` — класс `Bitrix` получает второй режим авторизации: OAuth с `client_endpoint`, токенами и колбэком обновления. Режим вебхука не меняется.

### Поток подключения

1. Claude регистрируется (`/register`, DCR) и открывает `/authorize` с PKCE и своим `redirect_uri`.
2. Наш `authorize` сохраняет запрос (client_id, redirect_uri, code_challenge, state Claude, scopes) под случайным ключом и перенаправляет браузер на `https://portal.example.ru/oauth/authorize/?client_id=<B24_CLIENT_ID>&state=<ключ>`.
3. Пользователь входит в портал и разрешает доступ. Портал возвращает на `https://mcp.example.synology.me/b24/callback?code=…&state=<ключ>&domain=…&member_id=…`.
4. `/b24/callback` проверяет `state`, обменивает `code` на токены через `oauth.bitrix.info` (с `B24_CLIENT_SECRET`), проверяет, что `client_endpoint`/`member_id` — наш портал, вызывает `user.current`.
5. Допуск: пользователь `ACTIVE`, не экстранет (тип пользователя «сотрудник»). Иначе — страница отказа, токены Битрикс24 не сохраняются.
6. `/consent` — страница: «Вы вошли как <ФИО>», **какая программа просит доступ**: название клиента из регистрации и хост его `redirect_uri` крупно (см. «Регистрация клиентов»), галочка «Только чтение» (если пользователь в списке администратора или включён глобальный режим — галочка стоит и заблокирована, с пояснением), кнопка «Подключить». Защита от CSRF (одноразовый токен формы, привязанный к ключу запроса).
7. После подтверждения создаётся «подключение» (grant): пользователь, токены Битрикс24, выбор «только чтение», клиент Claude. Выдаётся одноразовый код авторизации (10 минут) и браузер возвращается на `redirect_uri` Claude с `code` и исходным `state`.
8. Claude меняет код на наш access-токен (1 час) и refresh-токен (30 дней, с ротацией) в `/token`.

### Хранение (`DATA_DIR/store.db`)

- Клиенты DCR: client_id, метаданные (redirect_uris и т.д.).
- Ожидающие запросы authorize и коды авторизации: короткоживущие, удаляются после использования/истечения.
- Подключения: id, user_id портала, ФИО, client_id, read_only_user (галочка), токены Битрикс24 (access, refresh, срок), created/last_used.
- Наши access- и refresh-токены: храним только SHA-256 хэш, со ссылкой на подключение и сроком.
- Токены Битрикс24 шифруются AES-256-GCM ключом из `SECRET_KEY`.
- Периодическая очистка истёкшего.

### Обработка запроса к `/mcp`

- `requireBearerAuth` проверяет наш токен через провайдер → подключение.
- Эффективный режим «только чтение» = глобальный `READ_ONLY` ИЛИ галочка пользователя ИЛИ пользователь в `READ_ONLY_USERS` ИЛИ любой его отдел в `READ_ONLY_DEPARTMENTS`.
- На запрос создаётся (или берётся из кэша по подключению) `McpServer` с `registerTools(…, { client: Bitrix пользователя, readOnly, mode: "http" })` и транспорт Streamable HTTP. Состояние между запросами — только токены в хранилище; кэш `Bitrix` (в т.ч. кэш имён пользователей) — строго в пределах одного подключения.
- В режиме «только чтение» записывающие инструменты отвечают ошибкой, `b24_call` — только читающие методы (как сейчас), аннотации `readOnlyHint` выставляются по эффективному режиму (как сейчас для `b24_call`).
- Список отделов `READ_ONLY_DEPARTMENTS` действует и на все вложенные отделы: дерево отделов загружается через `department.get`, кэшируется (например, на час) и для пользователя проверяются все предки его отделов. *(Решение исполнителя дизайна: администратор, указав отдел, ожидает, что ограничение коснётся всех внутри.)*

### `b24_call` и утечка токенов в HTTP-режиме

*(Решение исполнителя дизайна по итогам ревью.)* Все приложения пользователей — одно локальное приложение, поэтому методы уровня приложения позволили бы одному пользователю влиять на других, а ответы некоторых методов содержат токен.

- **Запрещённые методы.** В HTTP-режиме `b24_call` отклоняет методы уровня приложения независимо от «только чтения»: `event.*`, `placement.*`, `app.*`, `imbot.*`, `imconnector.*`, `userfieldtype.*`, `bizproc.activity.*`, `bizproc.robot.*`, `user.option.*`, `entity.*` (хранилище приложения), `feature.*`, `messageservice.*`, `pay_system.*`, `sale.paysystem.handler.*`. Пользовательские поля CRM (`crm.*.userfield.*`) остаются разрешены. Список — константа с тестом; при сомнении метод запрещается.
- **Чистка ответов.** Весь вывод инструментов в HTTP-режиме проходит через фильтр, который удаляет из ссылок параметр `auth=…` (и `access_token=…`) и вычищает поля `DOWNLOAD_URL`, заменяя их пометкой. Это касается и `b24_call`, и всех остальных инструментов.
- Остальные 34 инструмента и `b24_call` с разрешёнными методами работают как в расширении.

### Обновление токенов Битрикс24 и перепроверка допуска

- Перед вызовом, если access-токен истекает в ближайшую минуту, или при ошибке `expired_token` — обновить через `oauth.bitrix.info` (`grant_type=refresh_token`), сохранить новую пару, повторить вызов один раз. Параллельные обновления одного подключения сериализуются.
- При каждом обновлении — `user.current`: если пользователь неактивен, подключение удаляется и запрос получает ошибку авторизации (Claude предложит переподключиться). Отделы пользователя обновляются, чтобы список `READ_ONLY_DEPARTMENTS` применялся без переподключения (в пределах часа).
- Если refresh-токен Битрикс24 истёк/отозван — подключение удаляется, клиент получает 401.

### `disk_file` в HTTP-режиме

Сохранение на диск сервера не имеет смысла. Текст, Office-текст и изображения — как сейчас (в ответе). Для остальных форматов и при `save=true` — возвращать метаданные и `DETAIL_URL` (ссылка на файл в портале, требует входа). `DOWNLOAD_URL` в ответ не отдавать: в OAuth-режиме он содержит токен пользователя. Параметр `save` в описании инструмента для HTTP-режима поясняется соответственно.

| Переменная | Назначение |
|---|---|
| `PUBLIC_URL` | `https://mcp.example.synology.me` (issuer, адреса в метаданных) |
| `B24_PORTAL` | `https://portal.example.ru` |
| `B24_CLIENT_ID`, `B24_CLIENT_SECRET` | из локального приложения |
| `SECRET_KEY` | ключ шифрования токенов (32 байта, base64) |

### Регистрация клиентов

*(Решение владельца: подключаться может любой MCP-клиент, не только Claude.)*

- Динамическая регистрация открыта для любых `redirect_uri` с `https://`, а также `http://localhost` / `http://127.0.0.1` (локальные клиенты вроде Claude Code).
- Страница подтверждения всегда показывает название клиента и хост, куда вернётся доступ. Если хост не из списка известных (`KNOWN_CLIENT_HOSTS`, по умолчанию `claude.ai`, `claude.com`, `localhost`, `127.0.0.1`), показывается заметное предупреждение: «Эта программа не из списка известных. Подключайте, только если сами начали подключение в ней» — и кнопку нужно подтвердить отдельной галочкой.
- Название клиента экранируется и обрезается; ему нельзя доверять — рядом всегда показывается фактический хост.
- Неиспользуемые регистрации (без подключений дольше 30 дней) удаляются при очистке.

### Безопасность

- Ограничение частоты запросов на `/register`, `/authorize`, `/token`, `/b24/callback` (express-rate-limit, уже в зависимостях SDK).
- `redirect_uri` Claude — только из зарегистрированных для клиента (проверяет SDK).
- Никаких токенов и `code` в логах; логи — метод, путь, статус, user_id.
- `trust proxy` для корректных адресов за обратным прокси DSM; сервер слушает только HTTP внутри контейнера, HTTPS — на прокси.

### Развёртывание

- `Dockerfile` (node:24-alpine, только production-зависимости, запуск `node server/http.js`, непривилегированный пользователь), `docker-compose.yml` для Container Manager (порт 3000 только на localhost NAS, том `./data:/data`, env из файла).
- Образ собирается на NAS из репозитория (Container Manager → Проект → из `docker-compose.yml`) или публикуется в GitHub Container Registry — на усмотрение исполнителя; инструкция в README.
- Инструкция по DSM: сертификат Let's Encrypt для `example.synology.me` с поддоменами; обратный прокси `https://mcp.example.synology.me:443 → http://localhost:3000`, с пробросом заголовков WebSocket не требуется, но нужны `X-Forwarded-*` и отключённая буферизация для потоковых ответов, если DSM это позволяет.

### Настройка на портале (для администратора)

Инструкция в README, по шагам: Приложения → Разработчикам → Другое → Локальное приложение; тип «Серверное»; галочка «Приложение использует только API»; путь обработчика `https://mcp.example.synology.me/b24/callback`; права: `user`, `department`, `task`, `im`, `disk`, `calendar`, `crm`, `sonet_group`; сохранить и скопировать `client_id` и `client_secret` в настройки контейнера. Точные названия пунктов меню и прав — сверить на портале во время спайка.

## Порядок работ

1. **Спайк (выбрасывается):** администратор создаёт приложение; скрипт локально строит ссылку авторизации, пользователь входит, копирует `code` из адресной строки (обработчик ещё не работает), скрипт меняет его через `oauth.bitrix.info`, вызывает `user.current`, `im.dialog.messages.search`, `disk.storage.getList`, проверяет обновление токена. Если не проходит — работа останавливается, и подход 2 проектируется отдельно; этот план его не включает. *(Решение исполнителя дизайна.)*
2. Вынос инструментов в `server/tools.js` с `ctx`, режим `.mcpb` и тесты без изменений поведения.
3. OAuth-режим в `Bitrix` (вызовы, обновление, `expired_token`).
4. Хранилище, OAuth-провайдер, страницы входа/согласия, `/mcp`.
5. Тесты: сквозной тест HTTP-режима на заглушке портала и `oauth.bitrix.info` (регистрация → authorize → callback → consent → token → вызов инструмента → обновление токена → режим «только чтение» из списка → отказ неактивному).
6. Docker, README, развёртывание на NAS, подключение из claude.ai и Claude Code, проверка на портале.

## Оставлено исполнителю

- Кэшировать `McpServer` на подключение или создавать на каждый запрос (stateless-транспорт) — по удобству и с учётом того, как SDK работает с сессиями.
- Вёрстка страниц входа/согласия/ошибок — простая, без внешних ресурсов.
- Точные сроки жизни наших токенов в пределах: access ≤ 1 час, refresh ≤ 30 дней.
- Сборка образа на NAS или через GHCR.
