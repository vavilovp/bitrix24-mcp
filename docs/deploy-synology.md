# Развёртывание на Synology NAS (Container Manager)

Удалённый режим: сервер работает на NAS в Docker, наружу выходит через обратный прокси DSM по HTTPS. Каждый сотрудник входит через свой портал Битрикс24, и инструменты работают от его имени.

Адреса в примерах: сервер `https://mcp.example.synology.me`, MCP-адрес для клиентов `https://mcp.example.synology.me/mcp`. Замените на свои.

## 1. Локальное приложение на портале Битрикс24

1. Откройте портал, раздел «Разработчикам» (или «Приложения» → «Разработчикам») → «Другое» → «Локальное приложение».
2. Тип приложения: «Серверное». Отметьте «Приложение использует только API».
3. Путь обработчика: `https://mcp.example.synology.me/b24/callback`. Если приложение уже создано раньше (например, с временным адресом `http://localhost:8765/b24/callback`), замените путь обработчика на этот.
4. Права: `user`, `department`, `task`, `im`, `disk`, `calendar`, `crm`, `sonet_group`.
5. Сохраните. Скопируйте `client_id` (вида `local.…`) и `client_secret`: они понадобятся в `.env`.

## 2. Сертификат и обратный прокси в DSM 7.2

Порт 443 NAS должен быть доступен из интернета, а `mcp.example.synology.me` указывать на NAS.

1. Панель управления → Безопасность → Сертификат → Добавить → Получить сертификат от Let's Encrypt. Домен `example.synology.me`, альтернативное имя `*.example.synology.me` (поддомены).
2. Панель управления → Портал входа → Дополнительно → Обратный прокси → Создать:
   - Источник: протокол HTTPS, имя хоста `mcp.example.synology.me`, порт 443.
   - Назначение: протокол HTTP, имя хоста `127.0.0.1`, порт 3000. Именно `127.0.0.1`, а не `localhost`: nginx в DSM может пойти на IPv6-адрес `::1`, а Docker публикует порт только на IPv4.
3. Правка правила → «Дополнительные настройки»: увеличьте время ожидания чтения прокси (например, до 300 секунд). Инструменты вроде `call_summaries` могут идти дольше стандартных 60 секунд.
4. Панель управления → Безопасность → Сертификат → Настройка: назначьте сертификат Let's Encrypt службе `mcp.example.synology.me`.

Порт контейнера публикуется только на `127.0.0.1:3000`, поэтому к серверу можно обратиться лишь через этот прокси (сервер доверяет заголовкам `X-Forwarded-*` одного прокси).

## 3. Настройка и запуск

Сервер поставляется готовым образом `ghcr.io/vavilovp/bitrix24-mcp` (amd64 и arm64), собирать его на NAS не нужно. На NAS нужны только два файла.

1. Создайте папку проекта, например `/volume1/docker/bitrix24-mcp` (File Station → общая папка `docker`). Положите в неё [`docker-compose.yml`](../docker-compose.yml) из репозитория.
2. Рядом создайте `.env` по образцу [`.env.example`](../.env.example) и заполните. Значение для `SECRET_KEY`:
   ```bash
   openssl rand -base64 32
   ```
   Обязательные переменные и их формат:
   ```ini
   PUBLIC_URL=https://mcp.example.synology.me
   B24_PORTAL=https://your-portal.example.com
   B24_CLIENT_ID=local.xxxxxxxxxxxxxxxx.xxxxxxxx
   B24_CLIENT_SECRET=...
   SECRET_KEY=...
   ```
   `PUBLIC_URL` и `B24_PORTAL` пишутся с `https://` и без завершающего `/` (адрес без схемы сервер дополнит `https://`). Комментарии в `.env` только на отдельных строках: текст после значения становится частью значения. При ошибке в настройках контейнер не запускается и перезапускается снова; причина видна в журнале контейнера (`Configuration error: ...`). Файл `.env` никогда не коммитится. Потеря `SECRET_KEY` делает сохранённые токены нечитаемыми, и всем придётся войти заново.
3. Container Manager → Проект → Создать: имя `bitrix24-mcp`, путь к папке проекта, источник «Использовать существующий docker-compose.yml», настройки Web Station не включать. Container Manager скачает образ и запустит контейнер. Либо по SSH из папки проекта: `sudo docker compose up -d`.

   Тег `latest` указывает на последнюю выпущенную версию (git-тег `vX.Y.Z`). Чтобы обновляться только осознанно, замените в `docker-compose.yml` `latest` на конкретную версию, например `1.2.0`.

   Команды `docker` по SSH в DSM выполняются через `sudo` (обычный пользователь не имеет доступа к сокету Docker). Container Manager в DSM 7.2 ставит Compose v2, команда `docker compose`; если её нет (старый пакет Docker), используйте `sudo docker-compose` с теми же аргументами.
4. Данные (SQLite с зашифрованными токенами) лежат в именованном томе Docker `bitrix24-mcp-data` (в проекте Compose он может называться с префиксом, например `bitrix24-mcp_bitrix24-mcp-data`). Том создаётся с правами пользователя контейнера и переживает пересборку и обновление контейнера. Посмотреть: Container Manager → Том, или по SSH `sudo docker volume ls`. Резервная копия: `sudo docker run --rm -v bitrix24-mcp_bitrix24-mcp-data:/data -v "$PWD":/backup alpine tar czf /backup/mcp-data.tgz -C /data .` (точное имя тома смотрите в `sudo docker volume ls`). Сброс (все сотрудники войдут заново): остановить проект и выполнить `sudo docker volume rm <имя тома>`; `sudo docker compose down -v` тоже удаляет том.
5. Проверка: `curl https://mcp.example.synology.me/healthz` возвращает `{"status":"ok"}`.

Логи: Container Manager → Контейнер → Журнал. Одна строка на запрос: `METHOD /path STATUS user=ID`.

## 4. Подключение клиентов

- claude.ai: Settings → Connectors → Add custom connector → URL `https://mcp.example.synology.me/mcp`. Дальше откроется страница входа портала Битрикс24 и страница согласия.
- Claude Code:
  ```bash
  claude mcp add --transport http bitrix24 https://mcp.example.synology.me/mcp
  ```
  Затем `/mcp` в Claude Code и вход через браузер.

## 5. Режим только чтения

В `.env`:

- `READ_ONLY=true` — для всех;
- `READ_ONLY_USERS=12,34` — ID пользователей, которым запись запрещена;
- `READ_ONLY_DEPARTMENTS=5,8` — ID подразделений (включая вложенные); требует права `department`.

Значения: `READ_ONLY` — `true`/`false` (также `1`/`0`, `yes`/`no`, `y`/`n`, `on`/`off`); списки — только целые положительные ID через запятую. Любое другое значение (например, комментарий после значения на той же строке) — ошибка настройки: сервер не запустится, причина будет в журнале контейнера.

Пользователь на странице согласия может сам выбрать режим только чтения.

Изменения `.env` вступают в силу только после пересоздания контейнера: `.env` читается при создании контейнера, а простой перезапуск (`docker restart`, кнопка «Перезапустить» у контейнера в Container Manager) оставляет старые значения. Пересоздать:

- по SSH из папки проекта: `sudo docker compose up -d` (Compose видит изменённый `.env` и пересоздаёт контейнер; данные в томе сохраняются). Если контейнер не пересоздался, `sudo docker compose up -d --force-recreate`;
- в Container Manager: Проект → выберите проект → «Действие» → «Остановить», затем «Действие» → «Собрать» (пересборка проекта): контейнер создаётся заново с текущим `.env`. Кнопка «Перезапустить» для этого не подходит.

Проверка: вызовите инструмент `b24_whoami` от имени нужного сотрудника; поле `read_only_mode` должно быть `true`. Для уже выданных доступов списки пользователей и подразделений применяются к каждому запросу, а состав подразделений сотрудника перепроверяется при очередном обновлении токена Битрикс24 (не реже раза в час).

## 6. Обновление

Новая версия публикуется автоматически: при git-теге `vX.Y.Z` GitHub Actions собирает образ и обновляет тег `latest`.

По SSH из папки проекта:

```bash
sudo docker compose pull
sudo docker compose up -d
```

В Container Manager: Проект → `bitrix24-mcp` → «Действие» → «Остановить», затем «Собрать» (скачивает свежий образ и пересоздаёт контейнер). Если в `docker-compose.yml` закреплена версия, сначала поменяйте её там.

Данные в томе `bitrix24-mcp-data` сохраняются (не используйте `down -v`).

Собрать образ локально из исходников (для разработки): `docker build -t ghcr.io/vavilovp/bitrix24-mcp:latest .`

## Прочие переменные

`KNOWN_CLIENT_HOSTS` (по умолчанию `claude.ai,claude.com,localhost,127.0.0.1`: остальные хосты требуют отдельной галочки на странице согласия), `B24_MEMBER_ID` (закрепить сервер за одним порталом), `B24_OAUTH_TOKEN_URL`. `PORT` (3000) и `DATA_DIR` (`/data`) заданы в образе, в `.env` их менять не нужно: порт контейнера должен оставаться 3000, иначе разойдутся проброс порта и обратный прокси.
