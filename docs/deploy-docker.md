# Развёртывание в Docker

Удалённый режим: сервер работает в контейнере Docker на любом хосте (VPS, домашний сервер, NAS), наружу выходит по HTTPS через обратный прокси. Каждый сотрудник входит через свой портал Битрикс24, и инструменты работают от его имени.

Адреса в примерах: сервер `https://mcp.example.com`, MCP-адрес для клиентов `https://mcp.example.com/mcp`. Замените на свои.

Вариант для Synology NAS (обратный прокси DSM и Container Manager) описан отдельно: [deploy-synology.md](deploy-synology.md).

## Что понадобится

- Хост с Docker и Compose v2 (команда `docker compose`), архитектура amd64 или arm64.
- Доменное имя, которое указывает на этот хост, и открытый из интернета порт 443.
- Обратный прокси с сертификатом HTTPS на этом хосте: nginx, Caddy, Traefik или любой другой (раздел 3).
- Портал Битрикс24, доступный с хоста и из браузеров сотрудников, и права администратора портала, чтобы создать локальное приложение.

## 1. Локальное приложение на портале Битрикс24

1. Откройте портал, раздел «Разработчикам» (или «Приложения» → «Разработчикам») → «Другое» → «Локальное приложение».
2. Тип приложения: «Серверное». Отметьте «Приложение использует только API».
3. Путь обработчика: `https://mcp.example.com/b24/callback`.
4. Права: `user`, `department`, `task`, `im`, `disk`, `calendar`, `crm`, `sonet_group`.
5. Сохраните. Скопируйте `client_id` (вида `local.…`) и `client_secret`: они понадобятся в `.env`.

## 2. Настройка и запуск

Сервер поставляется готовым образом `ghcr.io/vavilovp/bitrix24-mcp` (amd64 и arm64), собирать его не нужно. На хосте нужны только два файла.

1. Создайте папку проекта, например `/opt/bitrix24-mcp`, и положите в неё [`docker-compose.yml`](../docker-compose.yml) из репозитория.
2. Рядом создайте `.env` по образцу [`.env.example`](../.env.example) и заполните. Значение для `SECRET_KEY`:
   ```bash
   openssl rand -base64 32
   ```
   Обязательные переменные и их формат:
   ```ini
   PUBLIC_URL=https://mcp.example.com
   B24_PORTAL=https://your-portal.example.com
   B24_CLIENT_ID=local.xxxxxxxxxxxxxxxx.xxxxxxxx
   B24_CLIENT_SECRET=...
   SECRET_KEY=...
   ```
   `PUBLIC_URL` и `B24_PORTAL` пишутся с `https://` и без завершающего `/` (адрес без схемы сервер дополнит `https://`). Комментарии в `.env` только на отдельных строках: текст после значения становится частью значения. Файл `.env` никогда не коммитится. Потеря `SECRET_KEY` делает сохранённые токены нечитаемыми, и всем придётся войти заново.

   Контейнер публикует порт только на `127.0.0.1:3000` хоста. Если порт 3000 занят, добавьте в `.env` строку `HOST_PORT=3030` (или другой свободный порт) и укажите этот же порт в настройке прокси.
3. Запустите из папки проекта:
   ```bash
   docker compose up -d
   ```
   Compose скачает образ и запустит контейнер. При ошибке в настройках контейнер не запускается и перезапускается снова; причина видна в журнале (`Configuration error: ...`):
   ```bash
   docker compose logs
   ```
4. Проверка на самом хосте (до настройки прокси):
   ```bash
   curl http://127.0.0.1:3000/healthz
   ```
   Ответ: `{"status":"ok","version":"…"}` с номером запущенной версии.

Тег `latest` указывает на последнюю выпущенную версию (git-тег `vX.Y.Z`). Чтобы обновляться только осознанно, замените в `docker-compose.yml` `latest` на конкретную версию, например `1.2.2`.

Журнал: `docker compose logs -f`. Одна строка на запрос: `METHOD /path STATUS user=ID`.

## 3. HTTPS и обратный прокси

Сервер отвечает по обычному HTTP и рассчитывает, что HTTPS даёт обратный прокси перед ним. Подойдёт любой прокси, если он выполняет эти требования:

- принимает HTTPS на адресе из `PUBLIC_URL` с действующим сертификатом (например, Let's Encrypt);
- передаёт все запросы на `http://127.0.0.1:3000` (или на `HOST_PORT`). Именно `127.0.0.1`, а не `localhost`: Docker публикует порт только на IPv4;
- передаёт заголовки `Host`, `X-Forwarded-For` и `X-Forwarded-Proto`. По `X-Forwarded-For` сервер ограничивает частоту запросов с одного адреса; без него все клиенты считаются одним;
- перед сервером ровно один прокси. Сервер доверяет заголовкам `X-Forwarded-*` только от ближайшего. Если перед прокси стоит ещё один (CDN, балансировщик), ограничение частоты будет считать по адресу внешнего прокси;
- ждёт ответа не меньше 300 секунд. Инструменты вроде `call_summaries` могут идти дольше стандартных 60 секунд.

Порт контейнера не публикуется наружу, поэтому к серверу можно обратиться только через прокси на том же хосте. Прокси в отдельном контейнере не видит `127.0.0.1` хоста; для него сервер подключают через сеть Docker, как в примере Traefik.

### nginx и certbot

nginx установлен на хосте. Файл `/etc/nginx/conf.d/mcp.conf`:

```nginx
server {
    listen 80;
    server_name mcp.example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
    }
}
```

Затем certbot получает сертификат, сам дописывает в этот файл настройки HTTPS и перенаправление с HTTP:

```bash
sudo certbot --nginx -d mcp.example.com
```

### Caddy

Caddy установлен на хосте. Он сам получает и продлевает сертификат Let's Encrypt, передаёт нужные заголовки и не ограничивает время ответа. Файл `/etc/caddy/Caddyfile`:

```caddyfile
mcp.example.com {
	reverse_proxy 127.0.0.1:3000
}
```

```bash
sudo systemctl reload caddy
```

### Traefik

Если Traefik уже работает в Docker и следит за метками контейнеров, сервер подключается к его сети, а порт на хост не публикуется. Рядом с `docker-compose.yml` создайте `docker-compose.override.yml` (Compose подхватит его сам; нужна версия Compose 2.24 или новее):

```yaml
services:
  bitrix24-mcp:
    ports: !reset []
    networks:
      - traefik
    labels:
      - traefik.enable=true
      - traefik.docker.network=traefik
      - traefik.http.routers.bitrix24-mcp.rule=Host(`mcp.example.com`)
      - traefik.http.routers.bitrix24-mcp.entrypoints=websecure
      - traefik.http.routers.bitrix24-mcp.tls.certresolver=letsencrypt
      - traefik.http.services.bitrix24-mcp.loadbalancer.server.port=3000

networks:
  traefik:
    external: true
```

Имена сети (`traefik`), точки входа (`websecure`) и получателя сертификатов (`letsencrypt`) замените на те, что заданы в вашей настройке Traefik. Время ожидания ответа Traefik по умолчанию не ограничивает.

### Проверка

```bash
curl https://mcp.example.com/healthz
```

Ответ тот же, что и на хосте: `{"status":"ok","version":"…"}`.

## 4. Подключение клиентов

- claude.ai и приложения Claude: Settings → Connectors → Add custom connector → URL `https://mcp.example.com/mcp`. Дальше откроется страница входа портала Битрикс24 и страница согласия.
- Claude Code:
  ```bash
  claude mcp add --transport http bitrix24 https://mcp.example.com/mcp
  ```
  Затем `/mcp` в Claude Code и вход через браузер.

## 5. Режим только чтения

В `.env`:

- `READ_ONLY=true` — для всех;
- `READ_ONLY_USERS=12,34` — ID пользователей, которым запись запрещена;
- `READ_ONLY_DEPARTMENTS=5,8` — ID подразделений (включая вложенные); требует права `department`.

Значения: `READ_ONLY` — `true`/`false` (также `1`/`0`, `yes`/`no`, `y`/`n`, `on`/`off`); списки — только целые положительные ID через запятую. Любое другое значение (например, комментарий после значения на той же строке) — ошибка настройки: сервер не запустится, причина будет в журнале контейнера.

Пользователь на странице согласия может сам выбрать режим только чтения.

Изменения `.env` вступают в силу только после пересоздания контейнера: `.env` читается при создании контейнера, а `docker restart` оставляет старые значения. Пересоздать из папки проекта:

```bash
docker compose up -d
```

Compose видит изменённый `.env` и пересоздаёт контейнер; данные в томе сохраняются. Если контейнер не пересоздался, добавьте `--force-recreate`.

Проверка: вызовите инструмент `b24_whoami` от имени нужного сотрудника; поле `read_only_mode` должно быть `true`. Для уже выданных доступов списки пользователей и подразделений применяются к каждому запросу, а состав подразделений сотрудника перепроверяется при очередном обновлении токена Битрикс24 (не реже раза в час).

## 6. Обновление

Новая версия публикуется автоматически: при git-теге `vX.Y.Z` GitHub Actions собирает образ и обновляет тег `latest`.

Из папки проекта:

```bash
docker compose pull
```

```bash
docker compose up -d
```

Благодаря `pull_policy: always` в `docker-compose.yml` достаточно и одной команды `docker compose up -d`: она сама скачивает свежий образ. Если в `docker-compose.yml` закреплена версия, сначала поменяйте её там.

Проверка после обновления: `curl https://mcp.example.com/healthz` показывает новую версию.

## 7. Данные и резервная копия

Данные (SQLite с зашифрованными токенами) лежат в именованном томе Docker `bitrix24-mcp-data`. Compose добавляет к имени префикс проекта, например `bitrix24-mcp_bitrix24-mcp-data`; точное имя показывает `docker volume ls`. Том создаётся с правами пользователя контейнера и переживает обновление и пересоздание контейнера.

Резервная копия в текущую папку:

```bash
docker run --rm -v bitrix24-mcp_bitrix24-mcp-data:/data -v "$PWD":/backup alpine tar czf /backup/mcp-data.tgz -C /data .
```

Сброс (все сотрудники войдут заново): остановить проект и выполнить `docker volume rm <имя тома>`. Команда `docker compose down -v` тоже удаляет том, не используйте её при обычном обновлении.

## Прочие переменные

- `KNOWN_CLIENT_HOSTS` — по умолчанию `claude.ai,claude.com,localhost,127.0.0.1`; остальные хосты требуют отдельной галочки на странице согласия.
- `B24_MEMBER_ID` — закрепить сервер за одним порталом.
- `B24_OAUTH_TOKEN_URL` — адрес обмена токенов, если он отличается от стандартного.
- `HOST_PORT` — порт на хосте, на который публикуется контейнер (по умолчанию 3000).
- `PORT` (3000) и `DATA_DIR` (`/data`) заданы в образе, в `.env` их менять не нужно: порт внутри контейнера должен оставаться 3000.

Собрать образ локально из исходников (для разработки): `docker build -t ghcr.io/vavilovp/bitrix24-mcp:latest .`
